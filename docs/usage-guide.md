# 推荐用法接口与填写说明

更新：2026-10-29。本接口供 agent 根据官方产品与活动资料整理“这张卡适合怎么用”，只作阅读参考，不参与交易匹配、选卡排序、返现计算、迎新达标或个人剩余额度追踪。

## 放在哪里

在 `docs/catalog.json` 的某个 `products[]` 产品对象下增加可选的 `usageGuide`，与 `catalog`、`welcomePlans` 同级，不能放到 `catalog.rules[]` 内。

- 未准备好时**省略整个字段**，也可以写 `null`。不要求每张卡填写，不用空字符串或空对象占位。
- 有内容时必须是完整对象，至少一项场景。App 在“资料库产品预览”和“已添加卡片详情”显示推荐用法入口；未填写完全不显示入口。
- 这是编辑建议，不是银行原文；App 提供对应官方条款链接。不能用这里的文字替代 `catalog.rules` 的官方活动资料。
- 当前 24 款产品均已填写整卡综合指南（每张卡恰好 1 项策略）。下方仍是虚构模板，不可原样发布；合并前须确认客户端支持 usageGuide。

## JSON 模板

以下对象是 `usageGuide` 的值，示例 ID、链接和文字均须替换为核实后的内容；无实际活动依赖的产品级建议可用空的 `relatedOfferIDs`。

```json
{
  "summary": "【模板】一句话概括适合的用法与最重要限制。",
  "reviewedOn": "2026-10-29",
  "scenarios": [
    {
      "id": "example.mobile-payment",
      "title": "【模板】指定支付场景",
      "whenToUse": "【模板】地区、币种、消费类别及支付方式等必要前提。",
      "howToUse": "【模板】先完成所需登记，再使用条款指定的方式支付；写清操作和不适用情况。",
      "capNote": "【模板】写明回赠币种、金额、按月或整期、总回赠或额外回赠，以及主附卡或多卡是否共享。",
      "stopAfter": "【模板】仅在比例及上限明确时，说明对应合资格消费参考金额、推导前提，以及用满后为何可考虑换卡。",
      "warnings": ["【模板】尚需用户自行确认的资格、名额、排除类别或手续费。"],
      "relatedOfferIDs": ["example.offer.monthly"],
      "sourceURLs": ["https://example.com/official-terms"],
      "startsOn": null,
      "endsOn": null
    }
  ]
}
```

## 字段约定

| 字段 | 类型／限制 | 怎么填 |
| --- | --- | --- |
| `usageGuide` | 对象，可省略或 `null` | 不填不影响产品添加、官方权益与个人资料。 |
| `summary` | 必填字符串，1–90 字符 | 一两句话概括推荐用法，不宣称无条件“最划算”。 |
| `reviewedOn` | 必填 `YYYY-MM-DD` | 本次 agent 整理或复核建议的日期，不是活动开始日。 |
| `scenarios` | 必填数组，恰好 1 项 | 每张卡只有一份整体用卡策略。综合日常/优惠/迎新等可用活动，不按单条促销重复创建指南。 |
| `scenarios[].id` | 必填字符串，≤128 | 英文字母或数字开头，仅字母、数字、`.`、`_`、`-`；同产品内唯一，修订不改 ID，新场景新 ID。 |
| `title` | 必填字符串，≤64 | 简短、具体的场景标题。 |
| `whenToUse` | 必填字符串，≤130 | 适用地区、原币、类别、商户、支付方式、客户资格等；未知不要推断。 |
| `howToUse` | 必填字符串，≤220 | 自然语言写操作顺序、关键前提和优惠内容；说明总回赠还是额外回赠。 |
| `capNote` | 可省略／`null`／字符串，≤120 | 上限的金额、币种、周期、共享范围及适用部分。没有可靠资料就不填或明确“尚待核实”，不能写成无上限。 |
| `stopAfter` | 可省略／`null`／字符串，≤120 | “刷多少后考虑换卡”的静态参考，不是个人剩余额度，不填数字字段或可执行表达式。 |
| `warnings` | 可省略／`null`／数组，≤2 项，每项≤100 | 未知条件、费用、登记、排除项、名额及不保证到账等关键提醒。 |
| `relatedOfferIDs` | 必填字符串数组，≤20，可为空 | 只能引用**同一产品**的 `catalog.rules[].id` 或 `welcomePlans[].id`，不得跨卡引用；不能填活动名称或条款 URL，不重复。 |
| `sourceURLs` | 必填字符串数组，1–6 项，每项≤2048 | 能支持场景结论的公开官方 HTTPS 产品页／条款链接，不能带凭据，不重复。 |
| `startsOn` / `endsOn` | 可省略／`null`／`YYYY-MM-DD` | 该建议实际适用的时间范围；开始不得晚于结束。未知保持未知。多活动组合只写有证据的交集，不用核实日补成生效日。 |

全部文字是纯文本，不使用 HTML；不要靠 Markdown 链接隐藏来源或塞入可执行规则。必填文字不可留白，选填文字没内容就省略或 `null`，不要写空字符串。客户端与校验器都会检查字段、长度、日期和引用；官方来源的真实性与文字是否准确仍需提交者审查。

## Agent 编写流程

1. 找到准确产品 ID，区分白金／钻石／Signature、学生／普通版及扣账／信用卡，不借用另一版本的权益。
2. 读本产品当前 `catalog.rules`、`welcomePlans` 和对应银行研究文档；打开官方产品页和活动条款核实，不靠记忆或宣传“最高”数字。
3. 先确定有效期、登记、客户资格、合资格消费、支付方式、上限周期、共享范围及费用。仍未知的事实写入 `warnings` 或不作推荐，不当成已满足。
4. **只写 1 个整卡使用策略**，填 `whenToUse`、`howToUse`、所用多个活动的稳定 ID 与可追溯来源。活动下架或 ID 改变后必须复核依赖它的场景；删除活动不能留下悬空引用。
5. 只有比例和上限足够明确时，才写 `stopAfter`：说明例如“在额外回赠按合资格金额固定比例计算、且未使用共享上限的前提下，可用该部分上限除以该部分比例估算消费参考额”。公式前提、币种和周期必须齐全；有阶梯、积分兑换、额外／基础混合、最低门槛、多卡共享、名额、货币转换或其他不确定因素时，保留文字提醒，不强凑一个金额。
6. 不把“理论上用满”写成“你已刷满”；App 不读交易、不扣减额度，不保证银行认可资格或奖励到账。没有证据不能说哪个方案“全网最优”。
7. 不为建议创建新的活动事实或改官方规则。若依据已过期，更新建议或撤下；App 对已知结束日期标明“已结束”，日期未知会提示核实，不会从 `reviewedOn` 猜活动期限。
8. 更新真实 `reviewedOn`。仅编辑 schema、校验器或本文且未改快照时，不提升 `contentVersion`；真正填写／改动／移除建议会改 `catalog.json`，必须提高版本并填写真实 `publishedAt`。

## 兼容与验证

这是 Catalog V2 的可选字段扩展，个人 SwiftData 与同步格式不变。**旧 App 会拒绝产品未知字段，不会自动忽略 `usageGuide`，即使值为 `null` 也一样。** 2026-10-29 唯一使用者已明确无需照顾旧版兼容，本轮直接按支持 usageGuide 的当前客户端发布，不增加旧版分流服务；仍需验证实际快照解码与缓存。

在 Catalog 仓库运行：

```sh
python3 scripts/test_validate_catalog.py
python3 scripts/validate_catalog.py docs/catalog.json
git diff --check
```

真实快照变更还应使用 `--base` 检查版本递增，按 [PR 提交注意事项](pr-submission.md) 做客户端解码验证。主仓库新增接口的直接回归套件是 `CardUsageGuideTests`；已有 `CatalogV2Tests`、`BankLibraryTests` 验证缺省字段及资料库兼容。不要为了界面验收把模板写入真实用户资料，也不要把模板发布为卡片权益。

## 文案质量门槛

- 产品说明 `catalog.caveats` 不超过 180 字，`annualFeeNote` 不超过 110 字；每项 `rules[].notes` 不超过 300 字、迎新方案 `details` 不超过 250 字。
- `summary` 最多 90 字，突出“这张卡整体适合什么 + 核心限制”；仅一项整卡策略，综合重要的付款场景、金额和共享上限，不按活动拆分。
- 不能使用“本次整理”“暂未完整核对”“不视为”“此处不自动计算”“AI核实”“资料核实日当生效日”等开发者话术。缺失未知费用时保留未收录状态，不应替用户猜测免手续费或免年费。
- 重要限制例如登记、币种、MCC、上限共享、非叠加与新客资格不能删除；避免每段重复“以银行为准”。只有明确可推算的单独上限才能写 `stopAfter`；不确定就省略。
- 不把卡面来源说明放入消费提醒；卡面来源应写到素材文档。编辑指南不是官方活动规则，不可修改计算字段。

## 一张卡只写一个策略（2026-10-29）

- 每个 `products[].usageGuide` 对应 **一个完整的卡片使用方案**，`scenarios` 为兼容现有客户端保留数组结构，但恰好只填写一项，例如 `id: "guide.card-strategy"`。
- 综合多个活动时将它们全部列入 `relatedOfferIDs`，对应官方链接放在 `sourceURLs`；不是一个活动就要生成一个 Guide。
- 同卡活动生效期不一致时，**不要给整卡策略强行填一个统一 `startsOn`/`endsOn`**；在实际提示中明确当前季度或截止日期，靠活动本身保留精确起止时间。
- 日常策略优先，迎新点到为止；不要为了凑活动数而添加已经结束的优惠。
- App 首页及堆叠卡下方显示 `summary`，点击直接打开整个产品的详细用卡指南。严禁把 Guide 当成自动计算规则。
